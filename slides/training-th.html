LLM Wiki 101

ยินดีต้อนรับสู่ LLM Wiki 101 ค่ะ. ในเวลาประมาณสี่สิบห้านาทีต่อจากนี้ เราจะมาทำความเข้าใจ pattern ที่ Andrej Karpathy เสนอไว้ สำหรับการสร้าง knowledge base ที่มี language model คอยดูแลให้เรา — ไม่ใช่ wiki ที่ต้องมานั่งอัปเดตเองทุกบรรทัด และไม่ใช่ vector store แบบกล่องดำ แต่เป็นอะไรที่อยู่ตรงกลาง ที่ยังคงความแม่นยำไว้ได้แม้จะโตขึ้นเรื่อย ๆ. เราจะครอบคลุมทั้งพื้นฐานเชิงแนวคิดและรายละเอียดเชิงวิศวกรรม.

ใจความสำคัญ

นี่คือแก่นที่ทุกอย่างตั้งอยู่บนนั้น ในคำพูดของ Karpathy — wiki คือ artifact ที่คงอยู่และทบต้นไปเรื่อย ๆ ค่ะ. เทียบกับ RAG ทั่วไปที่เป็น stateless ทุกครั้งที่ query มันคำนวณคำตอบใหม่จากศูนย์ ไม่ได้จำอะไรไว้ระหว่างครั้ง. ส่วน LLM Wiki เป็น stateful — แต่ละ source ใหม่เพิ่มพูนเข้าไปใน synthesis ที่โตขึ้นเรื่อย ๆ. และสังเกตให้ดีว่าอะไรคือของใหม่จริง ๆ ตัว architecture เองเก่าแก่ราวเจ็ดสิบปี ของใหม่คือการมอบหมายงาน maintenance ทั้งการ link การ update การจดบันทึก ให้ language model ทำแทนเรา.

"The wiki is a persistent, compounding artifact." — Karpathy

  • RAG: stateless — re-derive ทุก query
  • LLM Wiki: stateful — สะสม synthesis
  • ความใหม่ไม่ใช่ architecture (เก่า 70 ปี)
  • ความใหม่คือ delegate maintenance ให้ LLM

3 layers, 3 operations

ระบบนี้มีสาม layer และสิ่งสำคัญที่ต้องเข้าใจคือ ใครมีสิทธิ์แก้แต่ละชั้นค่ะ. ชั้น Raw ไม่เคยถูกแก้ — เป็น source ดิบที่มนุษย์เป็นคน curate. ชั้น Wiki คือที่ที่ synthesis อยู่ LLM เป็นคน update ทุกครั้งที่ ingest โดยมีเราคอย review. ส่วนชั้น Schema ซึ่งเป็นกฎของระบบ เปลี่ยนนาน ๆ ครั้งและตั้งใจ เราเป็นคนเขียนเหมือนรัฐธรรมนูญ. และมีสาม operation ทำงานบน layer เหล่านี้ — ingest เปลี่ยน source ใหม่เป็น update, query ดึงความรู้ที่สะสมมาตอบ, และ lint ตรวจสุขภาพเป็นระยะ ซึ่งเดี๋ยวเราจะกลับมาพูดถึง.
LayerMutabilityAuthored by
Rawไม่แก้มนุษย์ (curate)
WikiUpdate ทุก ingestLLM (review)
SchemaRare, deliberateมนุษย์ (รัฐธรรมนูญ)

3 operations

  • Ingest — source ใหม่ → updates wiki หลายหน้า
  • Query — ดึงความรู้สะสมเพื่อตอบ
  • Lint — ตรวจสุขภาพเป็นระยะ

RAG vs LLM Wiki

ลองวาง RAG กับ LLM Wiki เทียบกันค่ะ เพราะคนมักสับสน. RAG เป็น stateless ต่อ query ดึง raw chunks มาเชื่อมกันด้วย embedding similarity เท่านั้น provenance ค่อนข้างหลวม. ส่วน wiki เป็น stateful และสะสม ดึง synthesised pages เชื่อมด้วย wikilinks ที่ชัดเจน และเก็บ provenance แน่นตั้งแต่ page ไป claim ไป source. RAG เด่นเรื่อง lookup เร็ว ๆ และตอบคำถามต่อ query, ส่วน wiki เด่นเรื่องความเชี่ยวชาญใน domain และงานวิจัย. และใน production เราไม่เลือกอย่างใดอย่างหนึ่ง — ใช้ wiki ก่อนเพราะถูก แล้ว fallback ไป RAG เมื่อต้องการข้อมูลล่าสุด.
มิติRAGLLM Wiki
StateStateless ต่อ queryStateful, สะสม
RetrieveRaw chunksSynthesised pages
ConnectionsEmbedding similarityWikilinks
ProvenanceChunk → source (หลวม)Page → claim → source (แน่น)
เหมาะกับLookupDomain mastery / research

Production hybrid: wiki ก่อน (ถูก), RAG fallback (current)

บรรพบุรุษ — Zettelkasten

แนวคิดนี้มีบรรพบุรุษที่ลึกมาก คือ Zettelkasten หรือกล่องบัตรบันทึกค่ะ. นักสังคมวิทยา Niklas Luhmann สร้างมันจากบัตรกระดาษราวเก้าหมื่นใบ และจากระบบนั้นเขาผลิตหนังสือราวห้าสิบเล่มกับบทความอีกราวห้าร้อยห้าสิบชิ้น. หลักสามข้อที่ทำให้มันเวิร์ก — atomicity หนึ่งความคิดต่อหนึ่ง note, cross-referencing เชื่อม note ด้วย link ที่ชัดเจน, และ unique ID ที่เสถียรสำหรับทุกใบ. ถอดกระดาษออก คุณจะเห็นชัดเลยว่า LLM Wiki ก็คือ Zettelkasten ที่มี language model ทำ maintenance แทนสิ่งที่ Luhmann ต้องทำด้วยมือ.

Niklas Luhmann สร้างกระดาษ ~90,000 ใบ ทำให้เขียน ~50 หนังสือ + ~550 บทความ

  • Atomicity — 1 ความคิดต่อ note
  • Cross-referencing — links ระหว่าง notes
  • Unique IDs — identifiers ที่เสถียร

"LLM Wiki = Zettelkasten + LLM ที่ทำ maintenance"

Genealogy

ลองดูสายวิวัฒนาการทั้งหมดค่ะ. ยุคห้าศูนย์ Zettelkasten กระดาษ ดูแลด้วยมือทั้งหมด. ยุคแปดศูนย์ ระบบ hypertext อย่าง NoteCards ยังส่วนใหญ่ manual. ตั้งแต่ปีเก้าห้า wiki ของ Ward Cunningham เพิ่มการทำงานร่วมกัน แต่ maintenance ยังเป็น manual. ยุคสองพันยี่สิบ เครื่องมืออย่าง Roam กับ Obsidian เพิ่ม plugin มาช่วย. และตั้งแต่ปีสองพันยี่สิบสี่เป็นต้นมา ก็คือ LLM Wiki ที่ language model เข้ามารับงาน bookkeeping. แต่ละยุคเก็บแก่นเดิมไว้ แล้วทำให้งานดูแลเป็นอัตโนมัติมากขึ้นทีละนิด.

Standard page template

นี่คือหน้าตาจริงของ wiki page หนึ่งหน้าครับ. ด้านบนคือ frontmatter — มี id, type, status, ค่า confidence, และ list ของ sources. ตามด้วย title, summary หนึ่งย่อหน้า, และหัวใจของหน้าคือ list ของ claims ที่ทุก claim มี source marker และ confidence number ของตัวเอง. สุดท้ายคือ relationships — typed link ไปยัง entity อื่น เช่น composes ชี้ไปที่ id ของอีกหน้า. โครงสร้างแบบนี้แหละที่ทำให้ทั้งระบบ machine-maintainable และตรวจสอบย้อนได้.
---
id: concept:llm-wiki
type: concept
status: active
confidence: 0.5
sources: []
---

# Title

## Summary
หนึ่งย่อหน้า

## Claims
- <Claim.> `[src: raw/...] {conf: 0.5}`

## Relationships
- composes → [[entity-id]]

Citation discipline (กฎ)

ถ้าจะจำกฎเดียวจากคอร์สนี้ ขอให้เป็นข้อนี้ครับ — ทุก claim ต้อง cite raw file พร้อม confidence number. วินัยข้อเดียวนี้ให้สามอย่าง. หนึ่ง บังคับให้มี grounding โมเดลจะ pad คำตอบด้วย prior ของตัวเองไม่ได้. สอง เปิดให้เกิด decay เพราะ claim ที่ confidence ต่ำและเก่า จะถูก flag ว่า stale ได้. และสาม เผย contradiction อย่างซื่อสัตย์ เพราะเมื่อสอง source ขัดกัน citation ทั้งคู่ยังอยู่. ส่วนคณิตศาสตร์ของ confidence ก็ง่าย ๆ แบบ reinforcement — observation แรกเริ่มที่ศูนย์จุดห้า แล้วการยืนยันอิสระแต่ละครั้งจะขยับเข้าใกล้หนึ่ง คือจุดแปด แล้วจุดเก้าสอง แล้วจุดเก้าเจ็ด.

ทุก claim cite raw file พร้อม confidence number

  • บังคับ grounding (ไม่ pad ด้วย priors)
  • เปิด decay (low conf + เก่า = stale)
  • เปิด contradictions (ทั้ง 2 citations อยู่)
conf = 0.5  (first observation)
conf = 1 - (1 - conf) * 0.6  (per reinforcement)

หลัง 1 reinforcement: 0.5 → 0.8
หลัง 2: 0.8 → 0.92
หลัง 3: 0.92 → 0.968

Ingest workflow

Ingest คือ workflow ที่คุณจะรันบ่อยที่สุด มีห้าขั้นครับ. หนึ่ง capture — เก็บ source แบบ verbatim ลงไฟล์ raw ที่มีวันที่ ยังไม่สรุปอะไร. สอง extract — ดึง entity ออกมา ตาม catalogue ที่ schema กำหนด. สาม write หรือ update wiki — และสังเกตว่านี่แตะหลายหน้า แต่ละหน้ามี source marker. สี่ reconcile งานจดบันทึก — index, log, และไฟล์ edges สำหรับ graph. ห้า summarise สิ่งที่เปลี่ยน — หน้าที่เพิ่มหรือแก้ contradiction ที่เปิด. Ingest ที่ดีมักแตะสามถึงสิบหน้า. ถ้าคุณแตะแค่หน้าเดียวทุกครั้ง แปลว่าคุณกำลังพลาด cross-reference ที่ทำให้ wiki มีค่า.
  1. Capture — verbatim ไป raw/YYYY-MM-DD-<slug>.md
  2. Extract — entities ตาม catalogue ของ SCHEMA
  3. Write/update — touch หลาย pages พร้อม [src:]
  4. Reconcile — index.md + log.md + graph/edges.jsonl
  5. Summarise — pages เพิ่ม/แก้, contradictions เปิด

Ingest ครั้งเดียวมัก update 3-10 pages. One-page ingest = พลาด cross-references

Lint workflow

Lint คือการตรวจสุขภาพเป็นระยะครับ ไม่ใช่ทุก ingest แต่ทุกสิบครั้งหรือรายสัปดาห์ถึงเดือน. มันมองหา orphan หน้าที่ไม่มีอะไร link เข้า, broken wikilink ที่อ้างไปหน้าที่ไม่มีอยู่, contradiction ที่เราแก้ด้วยการ supersede ไม่ใช่ลบเงียบ ๆ, stale claim ที่ confidence decay เกิน threshold แล้วถูก mark ว่า faded, และ citation integrity ที่ยืนยันว่าทุก source marker ยังชี้ไปไฟล์จริง. หลักการกำกับคือ supersession over deletion — audit trail ที่ดีสำคัญกว่า wiki ที่ดูเรียบร้อย.

เป็นระยะ ไม่ใช่ทุก ingest. ทุก 10 ingests หรือรายสัปดาห์/เดือน

  • Orphans — pages ไม่มี link เข้า
  • Broken wikilinks — [[X]] โดยไม่มี X
  • Contradictions — supersession, ห้าม delete silent
  • Stale — decay < 0.2 + 2× half-life → status: faded
  • Citation integrity — ทุก [src:] file มี

"Supersession over deletion." Audit trail สำคัญกว่าความเรียบ

Track B — Engineering patterns

นั่นคือจบ Track A ส่วนพื้นฐานครับ. ถ้าคุณมาเพื่อเข้าใจแนวคิด ตอนนี้คุณมีครบแล้ว. Track B เป็นของคนที่จะลงมือสร้าง — ยี่สิบห้านาทีต่อจากนี้จะลงรายละเอียดเรื่อง schema, tooling, failure mode, และการเชื่อมเข้ากับ agent. ถ้านั่นไม่ใช่คุณ ตรงนี้ก็เป็นจุดหยุดที่ดี.

สำหรับ builders ~25 นาที

Schema design — leverage สูงสุด

ในบรรดาทุกการตัดสินใจ schema คือสิ่งที่ leverage สูงที่สุด เพราะมันกำหนดทุกอย่างที่ตามมาครับ. มีสี่เรื่อง. เลือก entity catalogue ห้าถึงแปด type อย่าฝืนตั้งยี่สิบ. เลือก relation catalogue หกถึงสิบ ถ้าไม่แน่ใจใช้ default ที่สมเหตุสมผล. ตั้ง decay half-life ต่อ type — ของที่เปลี่ยนเร็วอย่าง tool อาจเก้าสิบวัน ของที่นิ่งอย่าง decision อาจเต็มปี. และเขียน privacy rule ให้ชัดว่าอะไรห้ามเข้า wiki เด็ดขาด. เหนือสิ่งอื่นใด เปลี่ยน schema ให้น้อยที่สุด มันคือรัฐธรรมนูญ ไม่ใช่ไฟล์ config.
  1. Entity catalogue — เลือก 5-8 types หลีกเลี่ยง 20
  2. Relation catalogue — 6-10 ใช้ default ถ้าไม่แน่ใจ
  3. Decay half-life ต่อ type — fast (tools): 90d. Stable (decisions): 365d
  4. Privacy rules — list ชัดของสิ่งที่ห้ามเข้า wiki/

Schema updates ควร rare. มันคือ constitution ไม่ใช่ config

Tooling: Obsidian + Git

คุณไม่ต้องใช้เครื่องมือพิสดารครับ Obsidian กับ Git ก็ครบแล้ว. convention แทบ map หนึ่งต่อหนึ่ง — หนึ่งไฟล์ markdown ต่อหนึ่ง entity เป็น native, wikilink ด้วยวงเล็บปีกกาคู่เป็น native และให้ backlink ฟรี, frontmatter เป็น native และ query ได้ผ่าน Dataview, graph view เป็น core plugin, และเพราะมันคือ folder ของไฟล์ text ล้วน ๆ มันจึงเข้ากับ Git ได้สมบูรณ์. plugin ที่ควรเพิ่มคือ Dataview, Templater, และ Obsidian Git สำหรับ version control อัตโนมัติ.

Failure modes

ทีนี้มาถึงส่วนที่ต้องพูดตรง ๆ ค่ะ — ระบบพวกนี้พังยังไง. ความล้มเหลวอันดับหนึ่งคือ claim drift — wiki ยังยืนยันสิ่งที่ source ไม่ support แล้ว. ตามด้วย orphan page ที่ไม่มี link เข้า, broken wikilink ที่ชี้ไปที่ว่างเปล่า, contradiction คือ claim ตรงข้ามเรื่องเดียวกัน, stale claim ที่ decay ควรทำให้ faded แล้ว, และ citation integrity ที่ไฟล์ถูกย้ายหรือลบ. เรื่องสำคัญของ drift คือมันไม่ได้พังหายนะตั้งแต่วันแรก — มันค่อย ๆ ทบต้นเงียบ ๆ ซึ่งเป็นเหตุผลว่าทำไม cadence ของ lint ถึงสำคัญ.
  • Claim drift — wiki พูดสิ่งที่ source ไม่ support แล้ว (#1)
  • Orphan pages — ไม่มี link เข้า ไม่อยู่ใน index
  • Broken wikilinks — targets ที่ไม่มี
  • Contradictions — claims ตรงข้าม subject เดียวกัน
  • Stale claims — apply decay; mark faded ห้าม delete
  • Citation integrity — cited file ย้าย/ลบ

Drift rarely catastrophic วันแรก. มัน compound

Provenance audit

นี่คือวิธีตรวจ provenance จริง ๆ สองระดับค่ะ. การเช็คแบบเร็วคือ shell loop สั้น ๆ — สำหรับทุกหน้า ทุก raw file ที่มัน cite ยืนยันว่าไฟล์นั้นยังอยู่ แล้ว print อะไรที่พัง. รันบ่อย ๆ ได้เพราะมันถูก. ส่วนการเช็คที่ลึกกว่าเป็น manual รายเดือน — สุ่มเลือกห้า claim แล้วยืนยันว่า raw ที่ cite ยังพูดสิ่งที่ claim อ้างจริง ๆ. ถ้าพลาดแม้แค่หนึ่ง นั่นคือสัญญาณว่าถึงเวลา full lint sweep แล้ว.

for page in wiki/*.md; do
  for src in $(grep -oE 'raw/[^]]+' "$page"); do
    [ -f "$src" ] || echo "BROKEN: $page → $src"
  done
done

# ลึกกว่า — random claim verification
# เลือก 5 claims รายเดือน เช็คว่า cited raw ยังพูด
# ถ้า 1+ fail → full lint sweep overdue

Integration กับ agents — context engineering

นี่คือจุดที่มันคุ้มค่าสำหรับระบบ agent ค่ะ. งานวิจัยของ Anthropic ชี้ความตึงเครียดนี้ชัด — เมื่อ context window โตขึ้น recall ของโมเดลกลับลดลง คุณยัดทุกอย่างเข้าไปไม่ได้. เราจึงแบ่งเป็นชั้น. wiki คือ memory ที่คงอยู่. RAG จัดการ retrieval แบบ just-in-time ของข้อมูลสดที่สุด. sub-agent ทำงานใน context window ที่สะอาด แล้วส่งกลับมาแค่ summary. และการประกอบคือ — ลอง wiki ก่อนเพราะถูก fallback ไป RAG เมื่อจำเป็น และถ้าเจออะไรใหม่จริง ๆ ก็ file กลับเข้า wiki เพื่อให้ระบบทบต้นต่อไป.

"As context window increases, model recall decreases." — Anthropic

  • Wiki = persistent memory layer
  • RAG = just-in-time retrieval
  • Sub-agents = clean context windows, return summaries
  • Composition: Wiki ก่อน → RAG fallback → file back ถ้าใหม่

5 health metrics

จะรู้ว่า wiki แข็งแรงไหม ให้ track ห้า metric ครับ. citation density ควรอย่างน้อยหนึ่ง citation ต่อ claim. provenance integrity ควรร้อยเปอร์เซ็นต์ — ทุก citation ชี้ไป raw ที่มีอยู่จริง. orphan rate ต่ำกว่าห้าเปอร์เซ็นต์. freshness คือยี่สิบถึงห้าสิบเปอร์เซ็นต์ของหน้าถูกแตะในเก้าสิบวันที่ผ่านมา — ต่ำไปแปลว่านิ่ง สูงไปแปลว่าปั่นป่วน. และ confidence median เกินศูนย์จุดหก โดย faded ต่ำกว่าสิบเปอร์เซ็นต์. baseline วันนี้ แล้ว re-check รายเดือน — cadence สม่ำเสมอนี่แหละที่จับ drift ได้ก่อนมันทบต้น.
Metricแข็งแรง
Citation density≥ 1.0 ต่อ claim
Provenance integrity100% citations point ไป raw จริง
Orphan rate< 5%
Freshness20-50% touched ใน 90d
Confidence median> 0.6; faded < 10%

Anti-patterns ที่ต้องเลี่ยง

รวม catalogue สั้น ๆ ของสิ่งที่ไม่ควรทำครับ. อย่าเก็บ schema ไว้ใน chat history — มันต้องอยู่ในไฟล์. อย่าตั้ง entity type เกินยี่สิบ นั่นคือ over-engineer. อย่ายุบทุกอย่างเป็น mega-citation อันเดียวท้ายหน้า มัน defeat การ audit. อย่าเขียน claim ที่ไม่มี confidence number. อย่าลบเงียบ ๆ ให้ supersede แทน. อย่าทำ single-page ingest คุณจะพลาด cross-reference. อย่า lint ทุก ingest มัน noise เกินไป. และอย่ารัน wiki โดยไม่มี version control เด็ดขาด.
  • Schema ใน chat history (ไม่ใน file)
  • 20+ entity types (over-engineered)
  • One mega-citation ท้าย page
  • Claims ไม่มี confidence number
  • Silent deletion แทน supersession
  • Single-page ingest (พลาด cross-references)
  • Lint ทุก ingest (noise เกิน)
  • ไม่มี version control บน wiki

Production checklist

ก่อนจะบอกว่า wiki พร้อม production ให้ไล่ checklist นี้ครับ. ฝั่งพื้นฐาน — สาม layer ครบ, ทำตาม page template, ทุก claim ถูก cite, และ wikilink ใช้ id ที่เสถียร. ฝั่ง engineering — schema อยู่ในไฟล์ไม่ใช่ chat, wiki อยู่ใน Git, ห้า metric ถูก baseline, privacy rule ชัดเจน, และสำคัญที่สุด คุณทดสอบมันด้วยทั้งมนุษย์จริงและ LLM จริงที่ขับมัน. ข้อสุดท้ายนี่แหละที่จับปัญหาที่การ review แบบนิ่ง ๆ มองไม่เห็น.

  • 3 layers ครบ
  • Page template ตาม
  • ทุก claim cited
  • Wikilinks ใช้ IDs

Engineering

  • ทดสอบบน human + LLM
